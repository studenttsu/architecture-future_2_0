# Переход ESB и интеграционный слой (Задание 1)

## 1. Переходный этап или целевое состояние?

Диаграмма описывает **целевую экосистему через ~1 год** (так подписан boundary на C4). При этом Camel и Legacy DWH на ней не «забыли убрать», а показывают **допустимый легаси-контур** — это прямо разрешено в условии landscape.

| Что на C4 | Роль через ~1 год |
|-----------|-------------------|
| Kafka, Integration Services, Airflow, Lakehouse | Основной путь новых потоков (S1–S4) и аналитики (S5) |
| Camel, SQL Server 2008 (DWH) | Только то, что ещё не перенесли: CDC, старые протоколы, bridge |
| Доменные сервисы, Data Products | Источник истины и бизнес-правил |

**Итог:** это не черновик «на полгода», а **целевая картина с сосуществованием** event-шины и узкой легаси-ESB. Kafka не вытесняет Camel за один релиз: сначала bridge, затем перенос маршрутов по одному (подход Strangler Fig — постепенно оборачиваем старое новым контуром).

---

## 2. Что будет с ESB (Apache Camel)

Стратегия: **не** «выключили ESB, поставили Kafka», а **сужаем зону ответственности Camel**.

| Этап | Срок | Camel | Новый контур |
|------|------|-------|--------------|
| A | 0–2 мес. | Работают текущие маршруты; пилот bridge в Kafka | Топики, Schema Registry, политики PHI |
| B | 2–6 мес. | Только легаси и DWH; **новую** бизнес-логику в Camel не кладём | События финтеха (S1), CDC в lakehouse (S4) |
| C | 6–12 мес. | Выключаем перенесённые маршруты | Партнёры (S3) через Integration Services; Kafka — основная шина |

Правила:

- **S1, S3** (новый финтех, фарма, оборудование) — сразу **Integration Services → Kafka**, без новых маршрутов в Camel.
- **S4** (разгрузка DWH) — пока `DWH → Camel → bridge → Kafka → Airflow → Lakehouse`; по мере готовности — `DWH → CDC/Connect → Kafka`, Camel на этом участке снимаем.
- Маршрут из Camel удаляем, когда есть: контракт в Schema Registry, ФЛК на входе, DLQ и мониторинг, согласование с доменом, регрессия отчётности (S4/S5).

К концу года Camel остаётся только там, где ещё нет адаптера (узкий protocol bridge). Целевой образ: **тонкий интеграционный слой** (адаптеры, ФЛК, аудит) + **Kafka** + **Airflow для batch/CDC**, без «умной» централизованной шины с бизнес-правилами.

## 3. Kafka + Airflow ≠ Camel: кто за что отвечает

| Функция в ESB | Где в целевой архитектуре | Почему не «всё в Kafka» |
|---------------|---------------------------|-------------------------|
| **ФЛК** | Schema Registry; проверка в Integration Services и Kafka Connect; правила в DataHub | Брокер передаёт сообщения; валидация схемы — отдельный слой |
| **Трансформации** | Data Product в домене; raw → curated в Lakehouse (Airflow/Spark) | Тяжёлые join и история — не задача realtime-брокера |
| **Маршрутизация** | Топики и ключи в Kafka; sync — API в Integration Services; старое — временно Camel | Вместо ветвлений в ESB — явные топики и версии контрактов |
| **Ретраи / DLQ** | Retry-топики и DLQ в Kafka; retry в Airflow для batch; outbox/inbox в сервисе для sync | У потоковых и пакетных цепочек разный SLA |
| **Бизнес vs интеграционная логика** | Правила — в доменных сервисах; шина — протокол, envelope, аудит | Требование задания: не наращивать логику в DWH и ESB |

**Роли на диаграмме:**

| Компонент | Делает | Не делает |
|-----------|--------|-----------|
| Event bus (Kafka) | События между доменами, триггер пайплайнов | Бизнес-правила, хранение «истины» |
| Integration Services | B2B, sync API, ФЛК, публикация в Kafka | Скоринг, KPI, клинические протоколы |
| Schema Registry | Версии контрактов | Трансформации данных |
| ETL (Airflow) | CDC, curated, окна загрузок (S4) | Realtime-маршрутизация как в ESB |
| Старая шина (Camel) | Легаси, bridge | Новые продуктовые правила |
| Data Lakehouse | Витрины для S5 без PHI | Операционная БД клиники/банка |

## 4. Разделение интеграционной и бизнес-логики

| Слой | Можно | Нельзя |
|------|-------|--------|
| Финтех / Медицина / ИИ | Правила продукта, лимиты, лечение, модели | Сливать всё в DWH без контракта |
| Data Product | Каноническая модель, обезличивание для аналитики | Дублировать те же правила второй раз в шине |
| Integration Services | ФЛК, маршрут в топик, аудит, B2B-auth | Расчёт KPI, кредитные решения |
| Camel (переход) | Маппинг легаси-формата, bridge | Новые ветвления по продукту |
| DWH (легаси) | CDC, регламентные срезы | Новые пакеты под каждый продукт |
| Lakehouse + портал | Self-service, KPI без медкарт | Сырые PHI в consumption |

**Пример S1:** «одобрить кредит» — в **Финтех Сервисах**; упаковка события `CreditApproved` и ФЛК — **Fintech Data Product** + **Integration Services**; попадание в витрину KPI — **Airflow → Lakehouse**, не новый маршрут в Camel.

---

## 5. Потоки и легенда на C4

**S1 (новый финтех-продукт):**

```
Финтех Сервисы → Fintech Data Product → Integration Services (ФЛК)
  → Event bus (Kafka) → Airflow → Data Lakehouse → Dremio / Портал
```

**S4 (легаси, переход):**

```
Legacy DWH → Старая шина (Camel, legacy bridge) → Kafka → Airflow → Lakehouse
```

После миграции участка S4: `DWH → Kafka Connect (CDC) → Kafka`, Camel отключается.

На диаграмме: **сплошные** связи доменов к Integration Services и далее к Kafka — целевой контур; **пунктир legacy bridge** от Camel — переходный, без новой бизнес-логики.

# Задание 2: домены, потоки данных и аргументация

## 1. Доменная декомпозиция

| Домен (как на C4) | Владелец (роль) | Ключевые данные / артефакты | Типовые сценарии | Граница с DWH и аналитикой | Что *не* кладём в DWH как новую логику |
|--------|------------------|-----------------------------|------------------|----------------------------|----------------------------------------|
| **Медицина** | Дирекция клиник, ИТ операционного контура | Операционные записи, расписания, медданные в операционной БД | Приём, лечение, учёт через клинический UI | Легаси-запись в DWH при необходимости; **не** тянуть PHI в корпоративную витрину | Правила финтеха, скоринг, модели ИИ |
| **ИИ-сервисы** | ИИ-подразделение | PHI в контуре моделей, агрегаты наружу | ИИ по снимкам/текстам, поддержка врача | Наружу — только контрактные агрегаты / data product | Общая витрина с сырыми медкартами |
| **Финтех** | Финтех (Go/Java) | Счета, платежи, договоры, события домена | Новый продукт, лимиты, платежи | События в платформу данных (**P2**), не новые пакеты в DWH | Бизнес-правила «внутри SQL Server 2008» |
| **Производство оборудования (будущее)** | Партнёры / закупки | Каталоги, заказы, серийники (по политике) | Интеграция производителя медэлектроники | Через контракты в шину → lakehouse | Прямой доступ к DWH |
| **Фармацевтика (будущее)** | Партнёры / закупки | Справочники, поставки (по политике) | Интеграция фарм-компаний | Аналогично: шина → lakehouse | Прямой доступ к DWH |
| **Портал и корпоративная аналитика** | CDO, аналитики направлений | Каталог, BI, запросы к lakehouse | S5: self-service **без** медкарт; быстрые отчёты | Читает curated/consumption; IAM | Сырые PHI в слое витрины |
| **Платформа данных** | Платформенная команда | Kafka, Airflow, схемы событий, API | Склейка доменов S1–S4 | Не «истина»; не замена медицинской БД | Долговременное хранение всех срезов как в DWH-монолите |
| **Legacy DWH** | DWH, финансы | История, регламентированные срезы | Отчёты «как было», CDC наружу | **CDC / batch** в платформу (**P2**) | Новые трансформации под каждый продукт |

## 2. Каталог бизнес-сценариев и меток (для DFD)

| ID | Сценарий | Участники | Смысл потока данных |
|----|-----------|-------------|---------------------|
| **S1** | Запуск **нового финтех-продукта** | Fintech → Integration → (при необходимости) Lakehouse / BI | События и справочники продукта выходят **из домена финтеха**, а не новыми пакетами в DWH |
| **S2** | **ИИ** над медицинскими данными | Clinical/DWH (PHI) → AI (ограниченно) → Integration | Данные для моделей остаются в **PHI-контуре**; наружу — только разрешённые результаты/фичи |
| **S3** | **Партнёры** (фарма и оборудование — отдельные домены на C4) | Партнёрский офис; домены «будущее» | B2B в платформу и lakehouse по контрактам, без прямого DWH |
| **S4** | **Отчётность и разгрузка DWH** | Legacy DWH / Camel → платформа → lakehouse → портал/BI | CDC и загрузки **без** новой логики в ядре DWH |
| **S5** | **Self-service без PHI** | Аналитик → портал / BI → слой запросов → lakehouse | RBAC; витрина без медкарт (landscape) |

## 3. Связь DFD и сценариев (трассировка)

- **P1** — клинические операции (UI ↔ **D1**). Поддерживает операционный контур клиники; PHI остаётся в операционном/легаси-контуре.
- **P2** — интеграционная платформа: точка входа **S1**, **S2**, **S3**, исходящий **S4** в lakehouse.
- **P3** — финтех-домен (**S1**).
- **P4** — ИИ-домен (**S2**); пунктир на потоках к **D1** подчёркивает ограниченный доступ к PHI.
- **P5** — lakehouse: **S4**, **S3** (курированные партнёрские данные), подготовка наборов для аналитики.
- **P6** — семантика, портал, BI (**S5**); читает **D2**, **D3**.

**DFD-0 (контекст):** процесс **0** «Экосистема…» агрегирует всю систему; внешние сущности **Клиника**, **Аналитик / сотрудник**, **Партнёры** и потоки к **0** соответствуют верхнему уровню тех же сценариев без внутреннего деталирования.

## 4. Аргументация: зачем бизнесу такое разделение

1. **Скорость вывода продуктов (time-to-market)**  
   Новые финтех-продукты и партнёрские интеграции меняют прежде всего **свои** домены и **контракты событий**, а не очередь согласований в монолитном DWH. Это сокращает цикл «идея → прод».

2. **Снижение зависимости от DWH**  
   DWH переводится в роль **наследуемого фундамента и CDC-источника**, а не места наращивания трансформаций под каждое новое направление — прямое следствие требования задания и отражено в Task1.

3. **Параллельные релизы и автономия подразделений**  
   Финтех (Go/Java), ИИ (Python) и будущие домены **фармы и производства оборудования** эволюционируют на **разных скоростях**, связываясь через **платформу данных**, а не через общую «релизную» очередь DWH.

4. **Регуляторика и доверие**  
   Разделение **PHI-контура ИИ** и **корпоративной аналитики без медкарт** снижает риск нерегламентированного использования медданных в self-service.

5. **Масштабирование под новые бизнесы**  
   Партнёры подключаются через **B2B-контракты** к интеграции и далее к lakehouse, не требуя «пробивать» ядро DWH новыми схемами.

Домены **Медицина, ИИ-сервисы, Финтех, производство оборудования (будущее), фармацевтика (будущее)** совпадают с доменными **SystemScopeBoundary** на [Task1/C4_future_2_0.drawio](../Task1/C4_future_2_0.drawio). Сквозные **портал**, **платформа данных** и **легаси-DWH** показаны там отдельными зонами. На DFD сценарии **S1–S5** по-прежнему реализуются **без переноса новой логики в DWH**, с разделением PHI и витрины.
